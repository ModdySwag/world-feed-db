### 1 · Liveness probing — ffprobe/ffmpeg one-shot checks, exact semantics

- ffmpeg docs: https://ffmpeg.org/ffmpeg.html · protocols: https://ffmpeg.org/ffmpeg-protocols.html · `-rw_timeout`/`-timeout` per protocol; `-analyzeduration`/`-probesize` in ffmpeg.html.
- KEY FACTS (mechanism): two levels — (a) **structure probe** (`ffprobe`) proves the container/stream parses; (b) **decode proof** (`ffmpeg -t 1 -f null -`) proves frames actually decode. Both must succeed; ffprobe alone is not enough.
  - **TESTED — structure probe on live HLS** (`Caltrans D10`, HLS):
    `ffprobe -v error -rw_timeout 15000000 -show_entries stream=codec_type,codec_name,width,height -of json "<m3u8>"`
    → exit 0 in **4.16 s**, JSON: `timed_id3` data stream + `h264` **720x480** video.
  - **TESTED — decode proof:** `ffmpeg -v error -nostdin -rw_timeout 15000000 -i "<m3u8>" -t 1 -f null -` → exit 0 in **3.70 s** (decodes 1 s of video, discards output; `-f null -` = no encoder cost).
  - **TESTED — dead host:** same ffprobe on an unresolvable host → exit **1** in **0.07 s**, stderr `Failed to resolve hostname … I/O error`. So DNS/connect failures are fast, pre-decode.
  - **TESTED — 200-OK-but-not-video (HTML page):** `https://example.com/` returns `200 text/html`; ffprobe → exit **1**, `Invalid data found when processing input`. ffmpeg `-t 1 -f null -` → exit **183** (non-zero; exact value differs per build — treat any non-zero as failure, don't pattern-match the number).
  - **TESTED — 200-OK still image (TfL jamcam JPEG):** ffprobe → exit **0**, parsed as a single-frame video stream; `ffmpeg -t 1 -f null -` → exit 0. **A still JPEG can look "decodable" — liveness for cameras needs the motion checks (§5/§6), not just exit codes.**
  - Timeouts: `-rw_timeout` is **microseconds** (15 000 000 = 15 s) — worked as tested. `-analyzeduration`/`-probesize` cap how much is read before deciding (defaults 5 s / 5 MB; lower = faster probes, more chances of "could not find codec parameters"). For RTSP, form is `ffmpeg -rtsp_transport tcp -i rtsp://…` plus a socket timeout (`-timeout` on newer builds, legacy `-stimeout`; check `ffmpeg -h demuxer=rtsp` on your build) — **not testable here: no public RTSP exists** (WV1 M4).
  - MJPEG-over-HTTP: `ffmpeg -f mjpeg -i "http://host/video.mjpg" -frames:v 1 out.jpg` — no working public MJPEG source to test (WV1 M3); keep as transport tier only.
- VERDICT: **ADOPT** — this is the verifier's ground truth. Build component: `verify` step 2 (decode proof) + step 1 (structure), with a hard per-probe timeout and exit-code + stderr classification (fast-fail classes: resolve/connect/timeout/HTTP-4xx/HTTP-5xx/not-video/no-track).

### 2 · HLS freshness — MEDIA-SEQUENCE / TARGETDURATION / PROGRAM-DATE-TIME / Last-Modified

- RFC 8216 (HLS): https://www.rfc-editor.org/rfc/rfc8216.txt — §4.3.3.2 `EXT-X-MEDIA-SEQUENCE`, §4.3.2.6 `EXT-X-PROGRAM-DATE-TIME`, §4.3.3.1 `EXT-X-TARGETDURATION` (read 2026-10-05).
- oscnord/hls-monitor (Rust): https://github.com/oscnord/hls-monitor — playlist-anomaly monitor with exactly these checks; README read 2026-10-05.
- KEY FACTS (mechanism): a "200 OK" playlist can be **frozen**: still served, but the media sequence never advances. Detect by polling the playlist twice and comparing:
  - `EXT-X-MEDIA-SEQUENCE` must **increase** as segments slide; regression or no-move beyond ~1.5–2× `EXT-X-TARGETDURATION` = stale manifest (oscnord implements "stale manifests … optional spec-compliant 1.5× target duration mode", plus target-duration-change and segment-count-shrink checks; CITED).
  - `EXT-X-PROGRAM-DATE-TIME` (absolute wall clock per segment) — a jump/discontinuity can be detected and, when present, gives a direct wall-clock freshness answer independent of your poll times.
  - `Last-Modified`/`ETag` on the playlist response: **TESTED** on Caltrans — the *master* master playlist and variant serve `Cache-Control: no-cache` + `ETag`, **no Last-Modified** (so do not rely on Last-Modified alone; sequence tracking is the portable method). Variant playlist content (TESTED):
    `#EXT-X-TARGETDURATION:11` · `#EXT-X-MEDIA-SEQUENCE:226` · `#EXT-X-DISCONTINUITY-SEQUENCE:0` · 3 × ~10 s segments.
  - Practical rule (PROPOSED, compiled from the above): poll playlist every 2× target duration; healthy = median ≥ 1 new sequence number per poll window; alert = 2 consecutive polls with unchanged sequence; kill = 4 polls unchanged or playlist fetch fails.
- VERDICT: **ADOPT** — cheapest freshness detector, zero decode cost; pairs with §1 for the "responds but old" state. Build component: `verify` step 1b (playlist watcher), feeds the state machine (stale vs live vs dead).

### 3 · LL-HLS (low-latency) — differences that matter to a checker

- HLS 2nd edition draft (LL-HLS): https://datatracker.ietf.org/doc/draft-pantos-hls-rfc8216bis/ — **draft-pantos-hls-rfc8216bis-22, "HTTP Live Streaming 2nd Edition"** (fetched 2026-10-05).
- go2rtc output notes: https://github.com/AlexxIT/go2rtc (HLS output section + `/api/stream.m3u8`).
- KEY FACTS: LL-HLS adds partial segments (`EXT-X-PART`), preload hints (`EXT-X-PRELOAD-HINT`) and server control (`EXT-X-SERVER-CONTROL`) so latencies drop from ~6–30 s to ~1–3 s; a freshness checker must then use much tighter windows (stale if no new part in ~2–3× part target instead of segments). Consequence for us: the §2 sequence-watcher thresholds should be *derived from the playlist tags* (target duration, PART-HOLD-BACK), not hard-coded. Public DOT traffic cams (Caltrans) are classic live HLS, not LL-HLS — treat LL-HLS as a supported case, not the default (PROPOSED). (verify the exact tag semantics against draft-22 before implementing.)
- VERDICT: **REFERENCE** — informs parameterization of §2; no separate component.

### 4 · Frozen-stream detection — ffmpeg `freezedetect` / `blackdetect` (battle-tested)

- ffmpeg filters docs: https://ffmpeg.org/ffmpeg-filters.html#freezedetect · reference implementation: louayfj/hls-stream-monitor https://github.com/louayfj/hls-stream-monitor (README read 2026-10-05).
- KEY FACTS (mechanism): `freezedetect` watches the luma of successive frames; when noise stays below `n` (dB) for duration `d`, it logs `lavfi.freezedetect.freeze_start` / `freeze_end` / `freeze_duration`. Exact tests today:
  - **TESTED (synthetic):** built `m.mp4` (3 s moving `testsrc`) + `mf.mp4` (same + `tpad=stop_mode=clone:stop_duration=4` = 4 s frozen tail), then:
    `ffmpeg -nostdin -i mf.mp4 -vf "freezedetect=n=-60dB:d=1" -map 0:v -f null -` → logged `lavfi.freezedetect.freeze_start: 2.9` (fires). Same command on the moving-only clip → no freeze lines. **Filter confirmed working as specified.**
  - **TESTED (live):** `ffmpeg -nostdin -i "<Caltrans m3u8>" -t 20 -vf "freezedetect=n=-60dB:d=2" -an -f null -` → no freeze events; decoded 599 frames in 1.14 s (18× realtime) — a 20 s freeze check costs ~1 CPU-second.
  - **CITED (production pattern):** louayfj/hls-stream-monitor runs ffprobe (codec/resolution) then a **single combined** ffmpeg call `-vf "blackdetect=d=0.5:pix_th=0.10,freezedetect=n=-60dB:d=1"` per channel, staggered across the scan window (`SCAN_INTERVAL_MS=120000`, `CONCURRENCY=4`, `PROBE_DURATION_SECONDS=3`, `PROBE_TIMEOUT_MS=10000` defaults), writes metrics/incidents to PostgreSQL with 30-day retention. It positions "combined filters" and its worker pool as deliberate CPU/threading optimizations — i.e., this is a practice someone already hardened.
  - `blackdetect` catches dead/hooded cams (all-black); `signalstats` (YAVG) gives a scalar brightness track usable for day/night sanity (§5).
- VERDICT: **ADOPT** — the cheapest *motion* oracle; run as verify step 3 on any candidate that passes step 2, or continuously on a rotating subset. Build component: `verify` step 3 (motion) — one combined `blackdetect,freezedetect` pass, capture-count gated.

### 5 · Frozen/`static` detection — two-sample pHash protocol (+ day/night sanity)

- imagehash (Python, pHash/aHash/dHash/whash): https://github.com/JohannesBuchner/imagehash — **3878★, last push 2026-10-05** (fetched today); `pip install imagehash` (PIL + numpy + scipy).
- KEY FACTS (mechanism): grab frame A, wait ≥ X minutes, grab frame B, compute pHash Hamming distance. Live cam → distance grows; looped/still/frozen cam → ~0.
  - **TESTED (tooling):** `imagehash` was not preinstalled; `py -3.11 -m pip install imagehash` then, on two Caltrans frames **30 s apart** (`ffmpeg … -frames:v 1`): phash A `d9d9fe763414050d`, B `fb9bb3f620077c00` → **Hamming distance 22** (64-bit hash, 720x480). Same-frame control → **distance 0**. So the metric separates "two distinct frames" from "identical frame" cleanly.
  - **PROPOSED protocol (not yet battle-tested in the wild — mark as design):** sample interval ≥ 5 min (calibrate per source class; many DOT cams refresh/rebroadcast on ~minute scales); classify `frozen` when distance ≤ 4–6 for two consecutive samples AND the stream still decodes (so a static-but-alive scene like a rural road at night is only "suspected static", never auto-killed on one sample); store both hashes + distance as status history; require 3 consecutive suspects before demotion to `static` (human-check tier). Thresholds need real-world calibration — start with the tested live=22 / identical=0 separation.
  - **Day/night sanity (PROPOSED):** cheap scene-aware guard for false freezes — luminance via `signalstats` (YAVG) or percent of near-black pixels; a night scene with IR illuminator switching causes legitimate large frame changes; conversely an all-black frame at noon is a strong "cam dead/covered" signal. Keep separate from the freeze verdict.
  - Related precedents checked: `gh search` for "frozen stream/camera detection" repos returned no maintained dedicated project (dead-end logged); the real precedents are the ffmpeg-filter monitors (§4) and the NVR watchdogs (§15). So pHash-as-scheduler is **our** design; pHash-as-metric is proven tooling.
- VERDICT: **ADOPT (tooling) / PROPOSED (protocol)** — the two-sample pHash is the frozen-cam tier for image-refresh (M7) sources, where `freezedetect` can't run (they're JPEGs, not video). Build component: `verify` step 3b (image tier) + dedupe (§17).

### 6 · Two-sample frame diff with ffmpeg only (SSIM/PSNR) — no Python deps

- ffmpeg filter docs: signalstats/ssim/psnr in https://ffmpeg.org/ffmpeg-filters.html.
- KEY FACTS: for pipelines already shelling out to ffmpeg, `ssim`/`psnr` between two saved frames gives the same verdict as pHash without Pillow/numpy. **TESTED** on the two Caltrans frames 30 s apart:
  `ffmpeg -i A.jpg -i B.jpg -lavfi ssim -f null -` → `SSIM All: 0.873963` (Y: 0.820142); `-lavfi psnr` → `PSNR average: 21.14 dB`. A frozen stream would be ≈1.0 SSIM / very high PSNR on both samples. Threshold proposals: SSIM < 0.995 → moving; ≥ 0.995 twice → static suspect (PROPOSED — calibrate; stills vs video frames differ in JPEG noise). VERDICT: **REFERENCE/ADOPT** — use as the decode-side fallback when imagehash isn't installed; the two-sample *concept* is shared with §5. Build component: `verify` step 3b alternative.

### 7 · YouTube live verification — yt-dlp (tested today) + Data API (key)

- yt-dlp docs/filters: https://github.com/yt-dlp/yt-dlp#filtering-formats (`--match-filter`, OUTPUT TEMPLATE fields; `live_status` ∈ is_live/is_upcoming/was_live/post_live/not_live).
- YouTube Data API v3: https://developers.google.com/youtube/v3/docs/videos (`snippet.liveBroadcastContent`), https://developers.google.com/youtube/v3/docs/search (`eventType=live`), quota: https://developers.google.com/youtube/v3/determine_quota_cost.
- KEY FACTS (local tests today, yt-dlp 2026.08.19):
  - **TESTED — field print:** `yt-dlp --simulate --print "%(live_status)s|%(is_live)s|%(title).60s" "https://www.youtube.com/@NASA/live"` → `is_live|True|Live Video from the International Space Station…`. On a normally-uploaded video: `live_status=not_live is_live=False`.
  - **TESTED — exit-code trick:** `--match-filter "is_live"` alone prints `does not pass filter (is_live), skipping` on a non-live video but **still exits 0** — useless as a check. `--break-match-filter "is_live"` on the same video → **exit 101**; on the live channel → exit 0. **So the reliable one-liner is:** `yt-dlp --simulate --break-match-filter "is_live" --print "%(id)s" "<URL>"; rc=$?` → rc==0 ⇒ live-ish, rc==101 ⇒ rejected (not live). Parse stdout id when rc=0.
  - **TESTED — environment warning:** this yt-dlp prints `WARNING: No supported JavaScript runtime could be found … YouTube extraction without a JS runtime has been deprecated` — install deno (or configure `--js-runtimes`) on the host, else some formats/extractions will silently degrade.
  - **CITED — Data API alternative (needs key):** `videos.list?part=snippet&id=…` → `snippet.liveBroadcastContent` (`upcoming`/`live`/`none`); `search.list` with `eventType=live` finds live items; quota table: **search.list = 100 units/call, videos.list = 1 unit, default 10 000 units/day** (so ~100 searches/day vs ~10 000 video lookups/day). Keyless yt-dlp is the cheaper path for arbitrary channels; API is for structured polls you must schedule in bulk.
  - Channel `/live` URLs resolve to the current broadcast and rotate ids; WV1 confirms they survive where `watch?v=` hits the bot wall (fallback `--extractor-args "youtube:player_client=android_vr"`).
- VERDICT: **ADOPT** — yt-dlp `--simulate --break-match-filter is_live` as the YouTube liveness probe; treat the Data API as an optional BYOK lane for quota-controlled bulk checking. Build component: `verify` YouTube adapter.

### 11 · iptv-org verification pipeline — exactly what runs in CI (and what doesn't)

- Repo: https://github.com/iptv-org/iptv (default branch **master**, last push 2026-10-05). Files read today: `.github/workflows/check.yml`, `.github/workflows/update.yml`, `scripts/core/streamTester.ts`, `scripts/commands/playlist/test.ts`, `scripts/commands/playlist/validate.ts`, `docs/workflows.md`, `docs/scripts.md`, `package.json`.
- KEY FACTS:
  - **CI does NOT test stream liveness on a schedule.** `check.yml` runs on PRs only: `playlist:lint` (m3u-linter) + `playlist:validate` (IDs/links structure via `@iptv-org/sdk`, duplicate/nonexistent-link statuses — not a network playout test). `update.yml` runs **daily at 0:00 UTC**: `api:load → playlist:update → lint → validate → generate → export → readme:update`, processing **approved GitHub issues** (streams:add / streams:edit / streams:remove) with a bot; broken links enter via the issue pipeline or via a maintainer running the tester.
  - **Liveness testing is a script (`playlist:test`), not CI:** `tsx scripts/commands/playlist/test.ts` — `eachLimit` with `--parallel` = **os.cpus().length** default; `--timeout` default **30 000 ms**; `--fix` "Remove all broken links found from files". It marks suspect streams when the status code is in `errorStatusCodes = [ECONNREFUSED, ENOTFOUND, ENETUNREACH, EPROTO, HTTP_404_*, HTTP_404_NOT_FOUND, HTTP_404_UNKNOWN_ERROR, HTTP_410_GONE]` (and only when the stream has no labels — labeled/geo-blocked streams are downgraded to warnings).
  - **The tester itself** (`streamTester.ts`): axios GET (responseType arraybuffer) with `AbortSignal.timeout(timeout)` and per-stream `User-Agent`/`Referer` headers, then **mediaInfo.js (WASM MediaInfo)** analyzes the downloaded bytes: `track.length > 0` ⇒ `OK`, else `NO_VIDEO`; errors classified as `TIMEOUT` (CanceledError), `HTTP_<code>_<STATUS>`, `AXIOS_<code>`, or `cause.code`. Note: media-info-by-download, **not ffprobe** — but it does read real container bytes, satisfying "not just a 200".
  - Reusable ideas worth copying: per-stream UA/Referer handling; small fixed error taxonomy; "labeled streams only warn" rule; removing dead links from the file rather than annotating them.
  - Related, externalized: **freearhey/iptv-checker** (same author as iptv-org's core lib): `npm install -g iptv-checker` — **ffprobe-based** Node CLI; defaults `-t 60000` ms, `-p` = CPU core count, `-r 0` retries, `-d 0` delay, UA `IPTVChecker/0.29.0`; checks local file/URL/stdin (CITED 2026-10-05). This is the ffprobe template the iptv ecosystem actually ships.
- VERDICT: **ADOPT (ideas) / REFERENCE (tool as a cross-check)** — copy the timeout/concurrency/error-taxonomy pattern into our verifier; use iptv-checker as an independent second-opinion CLI. Build component: `verify` step 2 cross-check + `update` issue-loop inspiration.

### 13 · livetrafficcam.com — a live "verified-live" signature at 21k-camera scale

### 14 · Self-heal precedents — NVR watchdogs (ZoneMinder, Frigate)

- ZoneMinder `scripts/zmwatch.pl.in`: https://github.com/ZoneMinder/zoneminder/blob/master/scripts/zmwatch.pl.in (read 2026-10-05, GPL).
- Frigate `frigate/watchdog.py` + `frigate/video/ffmpeg.py` (`CameraWatchdog`): https://github.com/blakeblackshear/frigate (read 2026-10-05) · config default `retry_interval: 10.0` in `frigate/config/camera/ffmpeg.py` ("Seconds to wait before attempting to reconnect a camera stream after failure").
- KEY FACTS:
  - **ZoneMinder zmwatch** (CITED, real production code): loops over monitors; a capture daemon is restarted when (a) shared memory invalid, or (b) `heartbeat_time` older than `ZM_WATCH_MAX_DELAY`; restarts via `$monitor->control('restart')`. Two safeguards designed against real incidents: a **per-monitor startup grace** (monitors never yet seen healthy are not restarted until they've had `ZM_WATCH_MAX_DELAY` to come up) and a **systemic-stall guard** — if the DB just reconnected or the watch loop was delayed >2× interval, skip restart/reboot actions for one pass ("the cause of the fleet-wide restart storms (each one coincided with a DB outage)"). Camera-reboot escalations only fire if the camera answers ping.
  - **Frigate process watchdog** (CITED): monitors FFmpeg/detector processes; clean exit (code 0) → not restarted; crash → restart with a budget: **`MAX_RESTARTS=5` per `RESTART_WINDOW_S=60`** then "backing off"; loop tick 10 s; detector stuck >10 s → restart the detector.
  - **Frigate camera watchdog** (CITED): `CameraWatchdog` tracks segment production; staleness threshold is **computed from the stream's own segment time**: `record_stale_threshold = max(120, 2 × segment_time + 30)` (tests assert 120 s main / 150 s sub); on restart it **grants a per-stream grace window** (so a just-restarted stream isn't re-killed), and restarts are paced by `retry_interval` (`time_since_last_restart >= sleeptime`). States published per-role as `offline/online`.
- VERDICT: **ADOPT (patterns)** — copy: heartbeat/stale-threshold per source, segment-time-derived thresholds, restart budget + backoff, startup grace, systemic-stall guard (skip a pass if the verifier itself was down), clean-exit≠failure. Build component: `self-heal` state machine.

### 15 · Self-heal design for world-feed-db — state machine + pools + re-discovery + serve-stale

- Precedents assembled from §11–§14 + MediaMTX always-available (https://mediamtx.org/docs/features/always-available) + the local WV1 sidecar (`server/world_feed.py`) (serve-stale + honest states, already implemented).
- KEY FACTS (PROPOSED design, with the cited precedent for each part):
  - **Health state machine per source:** `unknown → verifying → live → stale → suspect(frozen) → dead → retrying → dead(quarantined)`; transitions driven by §1 (decode), §2 (playlist freshness), §4/§5 (motion); every state carries `last_ok`, `last_err`, `age`; **serve-stale** everywhere (MediaMTX always-available; world_feed serve-stale; livetrafficcam's "shows when the feed last answered"). Never fabricate: `stale` and `dead` are terminal non-failure states in the UI sense (like ZM/Frigate offline roles).
  - **Backoff & restart budget:** exponential with cap (local AIS ingest already uses 5→60 s; ZM/Frigate patterns above) — e.g. `5, 15, 60, 300, 1800 s` then quarantine to a slow lane (re-check hourly). Restart budget per source: **N=5 failures / 60 min window → quarantine** (Frigate's 5/60 s logic, stretched for remote sources).
  - **Rotation pools per logical channel:** each logical "camera/feed" row owns an ordered list of concrete URLs (primary/backup/alternates; iptv-org's multiple stream URLs per channel and stream-id model (`channel@feed` with feed ∈ HD/Plus1/source-region) is the real-world shape; HLS master playlists give variant fallback within one source). Auto-swap on `dead`: try alternates in order, log the swap, promote the winner on 3 consecutive good checks; demote the loser to backup. Pool membership is a DB relation, not a rename.
  - **Re-discovery loop:** when a source dies, don't just mark it — re-scrape its origin directory (e.g. Caltrans `cctvStatusD*.json` (WV1), state DOT JSONs, agency page) and match by camera identity (§17) to find a moved URL; cadence per §19. Real precedent for the ingest side: iptv-org's issue → playlist:update loop + LES weekly revalidation; the re-discovery *triggered by death* is our addition (proposed).
  - **Watchdog on the verifier itself:** ZM's systemic-stall guard — if the verifier loop was down/skipped, do not mass-demote; mark one "uncertain" pass and re-check. Also a heartbeat row per worker (like ZM heartbeat) so a stuck verifier is detectable.
- VERDICT: **ADOPT design** — implementation graded against ZM/Frigate semantics; nothing here contradicts a cited production system. Build component: `self-heal` core (state machine, pools, rediscovery, watchdog).

### 16 · Dedupe & normalization — URL canonicalization + frame identity + camera identity

- RFC 3986 §6 (URI normalization): https://www.rfc-editor.org/rfc/rfc3986#section-6 · iptv-org `playlist:format` docs ("URL normalization, duplicate removal, removing invalid IDs, sorting") · LES `coordinates_quality` field · §5 pHash test.
- KEY FACTS (mostly PROPOSED rules; precedents cited):
  - **URL canonicalization:** lowercase scheme+host; strip default ports; sort query params; strip tracking params (utm_*); normalize YouTube forms (`youtu.be/ID`, `watch?v=ID`, `/live/ID` → one internal id — keep the *channel*/live resolution as a separate field); treat `…/master.m3u8` vs its variants as one logical source (record the variant set); percent-encoding normalization (RFC 3986 §6.2.2). iptv-org proves the practice at 10k+ playlist scale (their formatter is the cited implementation).
  - **Frame-level dedupe:** pHash (§5) with a per-source stored hash — identical hashes across *different* sources ⇒ same physical video (mirror/re-stream), flag "duplicate-of" rather than delete; identical hashes across *time* on one source ⇒ frozen (§5). Hash store: 64-bit integer column + Hamming compare (Postgres: `bit_count(a # b)`; SQLite: XOR via extension or compare in app code) (PROPOSED).
  - **Camera identity heuristics:** normalize name (casefold, strip punctuation/diacritics, drop "cam"/"camera"/directions); group by geo cell: geohash precision ~7 (~150 m) when coordinates are `exact`, coarser (city centroid) otherwise — LES's explicit `coordinates_quality` (exact|city|country_centroid) is the precedent for carrying that uncertainty instead of pretending precision; combine name similarity + geo distance + URL host/path family into a match score; require score threshold + human review for merges (PROPOSED).
- VERDICT: **ADOPT (rules) / PROPOSED (thresholds)** — build component: `ingest` normalizer + `db` identity tables.

### 17 · Storage — SQLite+FTS5 vs Postgres+PostGIS vs DuckDB; Datasette as viewer

- SQLite FTS5: https://sqlite.org/fts5.html · WAL: https://sqlite.org/wal.html ("only one writer at a time", WAL file, checkpointing) · scale reports read today (reports, not first-party tested): dev.to 1.7M patent rows → ~3 ms FTS5 queries vs 10–30 s LIKE (https://dev.to/soytuber/…-2bo7); cstsolution FTS5 index study — 100k docs full rebuild 1.36 s, 1M rebuild 17 s, index ≈0.76–0.85× text size, incremental-vs-rebuild crossover ~9% (100k) / ~5% (1M) daily change (https://cstsolution.com/blog/keeping-an-index-fresh/); medium 50M-row contentless-FTS5 case study (https://medium.com/charisol-pulse/…) — flag: `content=''` external-content pattern matters for storage.
- PostGIS: https://postgis.net/docs/using_postgis_dbmanagement.html §4.9 Spatial Indexes; ST_DWithin doc shows `CREATE INDEX … USING gist (geom)` and index utilization (fetched today).
- DuckDB: concurrency model (docs/1.3/connect/concurrency.md): **one writer process, or multiple read-only processes** — multi-process writes "not supported automatically"; spatial extension README lists "No support for spatial indexing" as a limitation **but the repo now contains `src/spatial/index/rtree/rtree.hpp` and a benchmark using `CREATE INDEX my_idx ON t1 USING RTREE (geom)`** (repo pushed 2026-10-01) — README text appears stale, RTREE indexing appears implemented (verify against the current release before relying).
- Datasette: https://docs.datasette.io/en/stable/full_text_search.html — publishes SQLite DBs as browsable/searchable sites, FTS configured via sqlite-utils; ideal viewer for a 100k-row catalog (static, no server ops).
- KEY FACTS / sizing logic: 100k–1M camera rows with geo + tags + status history is **small data** — SQLite handles it comfortably (FTS5 in the millions of rows is demonstrated; writes are the only contention point, and a single writer is exactly our updater's shape). Geo filters at this scale: bounding-box on indexed lat/lon columns + Haversine refinement in app code is fine; PostGIS earns its keep when you need true spatial operators at scale or concurrent writers. DuckDB is the wrong primary (single-writer process; concurrency model documented above) but excellent as an ad-hoc analytics engine over Parquet exports.
- VERDICT: **ADOPT SQLite + FTS5 + WAL as the primary store**, schema: `sources` (url, canonical_url, status, last_ok, last_err, hash) + `sources_fts` (FTS5 external-content) + `status_history` (append-only) + `pools` (logical channel ↔ source URLs) + `identity` (geo/name keys); **REFERENCE** PostGIS (upgrade path if/when >1 writer or real spatial ops needed); **REFERENCE** DuckDB (analysis of exports); **ADOPT** Datasette for the viewer/publish layer. Build component: `db` + `viewer`.

### 18 · Updater design — cadences, rate budgets, crash-safe crawl state

- Cadence data points (all CITED today or in WV1): Caltrans CCTV JSON refreshes ~2 min (WV1) → poll no faster than 2–5 min per district; **iptv-org** daily 00:00 UTC workflow (structural updates from issues) + manual/scripted liveness test with 30 s timeouts and CPU-count parallelism; **LES** weekly validate with `--limit 500` (sharded rotation through the catalog); **livetrafficcam** continuous rolling checks with 24 h correctness windows for flaky agencies; **YouTube Data API** quota 10 000 units/day (search=100, videos.list=1); Launch Library 2 anon = 15 req/h (WV1/world_feed.py shows the respect pattern: 900 s TTL keeps ~4/h).
- Scrapy as the proven crawl backbone: jobs/checkpoints https://docs.scrapy.org/en/latest/topics/jobs.html — `JOBDIR=crawls/<name>` persists scheduled requests + dupe filter + `spider.state` so a stopped crawl resumes; docs **warn** unclean shutdown can corrupt the job dir, so checkpoint on clean stop (and/or keep an independent state table). Rate governor: AutoThrottle https://docs.scrapy.org/en/latest/topics/autothrottle.html — `AUTOTHROTTLE_ENABLED`, `AUTOTHROTTLE_START_DELAY`, `AUTOTHROTTLE_MAX_DELAY`, `AUTOTHROTTLE_TARGET_CONCURRENCY` (docs describe it as "be nicer to sites instead of using default download delay of zero").
- KEY FACTS / PROPOSED design: three lanes — (a) **catalog refresh** (scrape directories; per-source TTL budgets; daily-ish), (b) **liveness rotation** (verify N sources per minute on a fair queue, prioritizing never-checked + recently-failed; adjust N so a full sweep is 24–72 h), (c) **slow lane** (quarantined sources hourly/daily + re-discovery). Per-source rate budget enforced by a token bucket keyed by host (e.g. Caltrans districts, DOT hosts) — never hammer a host because the catalog grew. Crash-safe state: the DB *is* the queue (`sources.next_check_at`, `lease_until` columns; updater claims rows with a lease, dies → lease expires → rows are re-claimed; idempotent per-source work). Status history append-only with retention (iptv-org-style pruning not needed; 30-day retention like louayfj's monitor is a fine default). Watchdog the updater (heartbeat row; §14 systemic-stall guard).
- VERDICT: **ADOPT** — Scrapy's JOBDIR/AutoThrottle as the conceptual + library backbone where scraping HTML; DB-lease queue for the verifier; token-bucket per host + honest TTLs. Build component: `updater` (scheduler, budgets, checkpointing), `self-heal` consumer.

## RECOMMENDED STACK (minimal; proposed-vs-proven labeled)

**Proven components (already verified on this host or by cited production systems):**
- **ffmpeg/ffprobe n9.0.1** — structure probe + decode proof + `freezedetect/blackdetect` + `ssim/psnr` frames. Produced today: exit codes, 20 s freeze check @ ~1.1 s, synthetic freeze caught, 599 live frames decoded.
- **yt-dlp 2026.08.19** — YouTube liveness via `--simulate --break-match-filter "is_live"` (exit 101 = not live) + `--print "%(live_status)s"` (needs a JS runtime installed on the host).
- **go2rtc v1.9.14** — local restream engine (HLS/RTSP/MJPEG/WebRTC in & out; frame/mjpeg APIs; verified working in WV1).
- **SQLite + FTS5 + WAL + Datasette** — store + viewer for 100k–1M rows with full-text and status history.
- **imagehash** (pip-installable; tested) — pHash (hamming 22 live-frame pair, 0 for identical).
- **Watchdog semantics proven in production:** ZoneMinder `zmwatch` (heartbeat + startup grace + systemic-stall guard), Frigate (`MAX_RESTARTS=5/60 s`, `retry_interval=10 s`, segment-time-derived stale thresholds `max(120, 2×segment+30)`).
- **iptv-org / LES / livetrafficcam** — verification cadence + honest-state vocabulary (verified-live / stale / dead) and the "check the image's timestamp, not just the 200" principle.

**Two-step liveness protocol (the required core; step order = cheap → expensive):**
1. **Cheap check:** HEAD/GET with 10 s timeout → 2xx + expected content-type; for HLS parse the playlist and require sane `EXT-X-TARGETDURATION` (and if seen twice, an advancing `EXT-X-MEDIA-SEQUENCE`); for YouTube run the yt-dlp break-match-filter probe; for image tiers require JPEG magic bytes + a server-reported freshness timestamp (Last-Modified/HEAD Date or in-image timestamp where available).
2. **Decode proof:** `ffprobe -v error -rw_timeout <15s> -show_entries …` (must list a video track) then `ffmpeg -v error -t 1 -f null -` (exit 0). Non-zero exit, or no video track ⇒ `dead` class (with the stderr-classified reason).
3. **Motion/freshness (camera tiers only):** (a) video — one combined `-vf "blackdetect=d=0.5:pix_th=0.10,freezedetect=n=-60dB:d=1"` pass on 10–20 s; (b) still images (M7 tier) — two samples ≥5 min apart, pHash hamming ≤ ~5 twice ⇒ `suspect(frozen)` (needs calibration); optionally SSIM fallback. All three steps write `last_ok/age/err` and feed the state machine; **serve-stale is mandatory** (never silently empty).

**Self-heal loop (PROPOSED, assembled from cited semantics):**
verify (rotating, fair queue, per-host token buckets) → classify (`live/stale/suspect/dead`) → on `dead`: advance to the next URL in the source's **rotation pool** (primary/backup), trigger **re-discovery** of the origin directory, and start the backoff clock (5 s→60 s→30 min→slow lane) with a **restart budget** (5 fails/60 min → quarantine); on 3 consecutive passes promote the winner and demote the loser; watchdog the verifier itself via heartbeat + "skip one pass after a stall" guard (ZM); every state transition lands in `status_history` and is served as honest UI states (verified-live / stale / dead / unknown).

**Deliberately not in v1:** PostGIS/DuckDB as primary store (upgrade paths, §17); MediaMTX/SRS/Ant Media engines (only if always-available streams or multi-tenant ingest is needed, §9/§10); streamlink (wrong tool, §10); HTML-page extraction tiers (they were the top failure class in LES — mark `unverified`, don't fake).

**Open items to verify before build:** exact RTSP timeout flag on this ffmpeg build; imagehash threshold calibration on real frozen cams; the LES "production selector"'s ffprobe parameters (not published); DuckDB RTREE status in the current release; livetrafficcam's check interval granularity (site says "rolling", not the exact rate).
